# StorageNetwork 游戏内性能实测：2026-10-16

## 结论

在本机、这份基准存档和 28 个持续发起请求的端口下，StorageNetwork 已埋点代码的稳定运行耗时可控。后台组通过现有 CPU 门限；库存明细与分类汇总同时打开时，整体 CPU 门限也通过，但分类汇总与零快照重建的严格 UI 门限未全部通过。首次展开面板还观察到一次约 318 ms 的计时尖峰，需要另行定位，不能据此宣称完全没有卡顿。

这次测量不是禁用模组与启用模组的 FPS 对照，也不是旧版与新版的三轮对照验收。

## 方法与口径

两组各采用连续 5 个完整的 60 秒窗口，跳过前 2 个预热窗口。后台组关闭库存面板；面板组展开固体服务器类别、第一台服务器的物品明细，并同时打开分类汇总，固定正常游戏速度。

表中 P95/P99 是每帧累计埋点耗时的分位数。窗口中位数是五个窗口对应分位数的中位数，不是把五分钟全部帧重新合并后的分位数。计时覆盖模组已有埋点，包括其中同步调用的引擎工作；不覆盖所有未埋点代码，也不是进程独占 CPU 时间。线程被调度暂停或 GC 等也可能体现在耗时中。

运行环境不支持逐线程分配跟踪，日志明确输出 `modAlloc=unsupported`。`gen0` 和 `managedDelta` 是游戏进程层面的观测，不能归因为本模组的 GC 次数或内存增量。

面板组数值较低不能解释为打开面板会提升性能：只有各一轮运行，模拟活动、复制人状态及后台负载并非完全相同，未建立因果对照。

后台组的主要埋点耗时来自搬运；采用窗口未出现来源回退扫描。游戏整体一分钟平均 FPS 在后台组为 31.7–51.4，面板组为 59.2–76.6。该差异进一步说明整局模拟与机器状态会影响帧率，不应把 FPS 差值直接归为面板影响。

### UI 严格验收

- 主面板：采用窗口内单次刷新 P95 桶上界均为 0.5 ms，P99 桶上界均为 1 ms，符合对应 UI 门限。
- 分类汇总：5 个窗口的单次刷新 P95 桶上界均为 1 ms，未达到 0.5 ms 目标；其中一个窗口 P99 桶上界为 2 ms，未达到 1 ms 目标。这里是直方图桶上界，不能当作精确分位数。
- 一个窗口记录到 1 次世界快照重建，未达到零重建的严格要求；该次重建的触发原因尚未定位。
- 因以上指标，`panel.json` 的整体 `AcceptancePassed` 为 `false`，保留全部 7 条失败记录；没有放宽门限使报告通过。

### 预热与操作尖峰

- 面板组预热窗口记录到 `MainPanel` 单次最大耗时 **318.317 ms**。随后五个稳定窗口的模组累计最大单帧耗时为 7.921 ms。这是值得继续分析的首次展开/初始化阶段问题，尚无足够证据锁定具体函数或原因。
- 后台组完成七个窗口后，界面被切换到交易窗口，速度也可能改变；用户随后确认会停止操作以便继续测试。第八个窗口含分类汇总、主面板和布局活动，并记录到累计最大值 **340.458 ms**、搬运单次最大值 **336.412 ms**。它不符合“面板关闭”的实验条件，未并入后台稳定组，但原始日志及失败报告完整保留。
- `background-stable-player.log` 只截取原始会话前七个完整窗口；采用第 3–7 窗口。不是按数值挑选五个最好窗口。

## 边界与后续定位顺序

本存档的订单与保有量规则为空，因此不覆盖大量复杂订单规划压力，也不覆盖成百上千端口、海量物品对象、复杂 DIY 蓝图或长期内存增长。大质量不等于大量物品对象，250 吨不能代表碎片数量压力。

若继续优化，优先复现并细分首次面板展开的约 318 ms 尖峰，其次分析分类汇总的刷新成本及那一次世界快照重建。要评价相对旧版的改善比例，需要固定环境，按现有流程各做三次独立运行。
