# StorageNetwork 主线程算法优化记录

日期：2026-10-16。对应四项工作：面板首次构建分帧、仓内候选索引、增量分类汇总与稳定排序、失败请求按相关变更唤醒。

## 实现

1. **面板构建分帧**：主行、服务器子行和物品控件经队列逐帧生成。每帧最多执行两项，协作预算 0.75 ms；隐藏的行暂停、销毁的行丢弃，清空面板会释放待建工作。恢复滚动位置等待队列完成，用户主动滚动会取消恢复。另将场景首次登记提前到加载后的 Update，最多登记 32 个对象或消耗 0.75 ms 后让出；严格模拟/API 读取仍同步补完登记，界面等待完整目录后展示。
2. **仓内候选索引**：对有材料筛选的固体、气液输出懒建标签桶，后续只读取候选物品；多标签合并保持原生物品顺序并去重。不筛选时保留原生遍历。索引随仓库事件、已知搬运和未知失效清空；实际搬运前仍执行原有物品资格判断。非登记仓库及诊断全扫描模式保留原生读取。
3. **增量分类汇总**：记录各仓库版本和贡献，只替换变化仓库、折叠受影响材料。保留原来源加法顺序与代表物品选择，避免长期反复相减造成误差。材料集合、名称或语言排序规则变化才重新排序；质量变化复用顺序。
4. **失败请求唤醒**：六类端口、生产请求/产出回存和普通仓库连接器，仅在请求没有搬动物品时进入等待。相关材料、目标库存、连通性或设置变化后在正常更新节拍重试；默认每 5 秒兜底，生产请求保留更长的已有配置间隔。成功请求不进入等待。自身库存变化直接解除等待，清理组件时解绑事件。

以上均减少主线程的重复工作，没有引入后台线程或 GPU 运算。

关键证据包括：

- 1,003 个物品的稀疏材料查询预热后只返回 4 个候选，不再检查另外 999 个物品；覆盖多标签顺序、同数量替换、事务内未知失效和带仓库变更事件的动态标签变化。
- 增量汇总经过 200 次随机来源增删，与按原顺序全量折叠逐次比较；单个来源变化仅折叠受影响键。
- 排序测试覆盖仅质量变化、名称变化和材料消失；队列测试覆盖时间/数量预算、隐藏恢复、销毁丢弃和嵌套任务延后。
- 等待门测试覆盖相关版本变化、兜底重试、成功解除等待；内容索引测试覆盖无关已知材料及不可达世界不唤醒、未知本地变化及连通性变化唤醒。

## 边界

- 队列和场景登记是协作预算，单个控件构造、组件注册或引擎 FindObjects 调用不可中断，可能超过 0.75 ms。加载尖峰仍存在；没有承诺首次打开完全无卡顿。
- 候选缓存依赖仓库变更/失效协议。绕过这些协议的第三方直接改物品标签不属于本轮验证覆盖。
- 当每个仓库都持续改变时，增量汇总仍需处理所有变化来源；它不能保证每次刷新都达到严格 UI 耗时门限。
- 无关世界和材料过滤避免部分空转，但失败请求唤醒仍有轻量版本检查；相关世界未知变更会保守唤醒。
- 大质量不等于大量物品对象。本轮不覆盖海量碎片、大量复杂订单和长期内存增长；无逐线程内存分配数据，不把进程级 GC 归因于本模组。
- 没有做每版三次独立的 FPS 对照，不报告整体帧率提升百分比。
